# 알림 센터

중요한 움직임과 센서 문제를 보호자가 놓치지 않고 확인하는 화면(`/notifications`, 상세 `/notifications/:id`)입니다.

## 가장 중요한 구분: 읽음 ≠ 해결

| 값 | 뜻 | 누가 바꾸나 |
|---|---|---|
| **읽음 여부** (`read`) | 보호자가 이 알림을 **봤다**는 표시. 보호자마다 따로 저장 | 보호자가 "읽음으로 표시" / "모두 읽음" |
| **처리 상태** (`status`) | 진행 중 → 확인함 → 종료. 상황을 **확인·종료**했는지 | 보호자의 "확인했습니다"·"알림 종료", 또는 조건이 풀려 자동 종료 |

- 알림을 읽어도 처리 상태는 **바뀌지 않습니다.** 읽었지만 진행 중인 알림에는 "읽었지만 아직 확인 처리하지 않은 알림입니다"라고 적습니다. 반대로 "확인했습니다"를 눌러도 읽음이 되지 않습니다.
- 읽지 않은 수가 0이어도 진행 중인 알림이 있을 수 있습니다. 빈 상태·요약·확인 대화상자가 그렇게 알립니다.
- 열린 긴급 알림은 읽어도 재알림 대상으로 남습니다. (확인하지 않았으므로)

## 알림 데이터

| 요구한 항목 | 구현 (`Alert` / `AlertItem`, `packages/shared/src/alerts.ts`) |
|---|---|
| ID · 제목 · 내용 | `id` `title` `message` (문구는 확정적 표현을 쓰지 않음) |
| 생성 시각 | `triggeredAt` (ISO 8601, 화면에서 한국 시간으로 표시) |
| 읽음 여부 | `AlertItem.read` — **읽는 보호자 기준**이라 목록·상세·읽음 응답에만 있고, 모든 화면에 뿌리는 실시간 알림(`Alert`)에는 없음 |
| 알림 중요도 | `severity`: 참고(INFO) · 확인 필요(NOTICE) · 즉시 확인 권장(URGENT). "중요 알림" = 확인 필요 이상 |
| 관련 이벤트 ID | `relatedEventIds` — 움직임 기록의 이벤트 ID(최신순 최대 5개). 움직임 알림은 근거 신호 `mov_…`, 센서 알림은 같은 때(앞뒤 2분) 남은 센서 상태 기록 `sta_…`. 가리킬 기록이 없으면(알림 전달 실패) 빈 배열 |
| 관련 센서 ID | `sensorId` · `sensorName` (센서와 무관한 알림은 null) |
| 전달 상태 | `deliveryState`(대표 값) + 상세의 채널별 전달 기록 |

### 알림 유형

| 요구한 유형 | `AlertType` | 비고 |
|---|---|---|
| 침대 이탈 추정 | `BED_AREA_ACTIVITY`, `BED_TO_PATH` | **이름 변경:** "이탈"은 이 프로젝트가 금지한 표현이라 "침대 주변 움직임" / "침대 주변에서 이동 경로로 이어진 움직임"으로 씀. 단일 센서 신호로 침대를 벗어났는지는 알 수 없음 |
| 현관 주변 움직임 | `ENTRANCE_APPROACH` | 야간 현관 센서 신호 |
| 반복적인 움직임 | `REPEATED_MOVEMENT` | |
| 센서 연결 끊김 | `SENSOR_OFFLINE` | |
| **센서 연결 복구** | **`SENSOR_RESTORED` (새로 만듦)** | 끊김이 기록된 센서가 돌아오면 생김. 알려 주기만 하면 되는 정보라 **참고 수준·만들 때부터 종료(자동 종료)** 상태, 소리·배너 없음. 처음 연결은 복구가 아니라서 만들지 않음. 끊겨 있던 동안의 움직임은 기록되지 않았을 수 있다고 적음 |
| 센서 배터리 부족 | `LOW_BATTERY` | |
| 시스템 오류 | `DELIVERY_FAILED` ("알림 전달 실패") | **현재 실제로 생기는 시스템 오류는 이것 하나뿐**이라 별도 `SYSTEM_ERROR` 유형을 만들지 않았음 |

## 전달 상태 (5가지)

서버가 **알 수 있는 범위에서만** 구분합니다. (`classifyDelivery`, `aggregateDeliveryState`)

| 상태 | 언제 | 의미 |
|---|---|---|
| 대기 | 아직 보내지 않음(시도 0회) | |
| 전송 시도 | 시도했고 다시 시도할 예정 | |
| **전송 성공** | **앱 화면 알림**을 열려 있는 화면에 보냄 | 보호자가 읽었다는 뜻은 아님 |
| **전달 확인 불가** | **푸시·문자·카카오** 등 외부 서비스에 넘김 | 푸시 서비스에는 전달했지만 **기기에 도착했는지는 확인할 수 없음**. 성공이라고 쓰지 않음 |
| 전송 실패 | 모든 시도 실패 | |

- **재시도하지 않는 실패:** 푸시 구독이 없거나(등록한 기기 없음) 모두 만료되어 지워진 경우처럼 다시 보내도 같은 결과인 실패(`DeliveryError.retryable=false`)는 3회를 채우지 않고 바로 "전송 실패"로 확정합니다. 일시적인 네트워크·푸시 서비스 오류만 30초·2분 뒤 다시 시도합니다.
- 채널은 앱 화면·브라우저 푸시·**스마트워치(`WATCH`, 항상 "연동되지 않음" — [WATCH_INTEGRATION.md](WATCH_INTEGRATION.md))**·문자·카카오입니다. 채널별 지원 여부는 `GET /api/system/channel-support`.
- 연동되지 않은 채널(`NOT_CONFIGURED`)과 확인·종료로 멈춘 전달(`CANCELLED`)은 이 5가지에 속하지 않고 "연동되지 않음"·"전달 중단"으로 따로 보입니다.
- 알림 하나의 대표 상태는 도착에 가까운 쪽(성공 > 확인 불가 > 시도 > 대기 > 실패)이며, 일부 채널이 실패했으면 목록에 "일부 채널 전송 실패 N건"을 함께 보여 줍니다. 전달 대상이 없으면(참고 수준 등) 상태 배지 없이 전달 기록을 말합니다.
- 실제 기기 수신 여부를 확인했다고 표시하는 곳은 없습니다. (테스트가 화면 문구를 검사)

## API

| 요청 | 설명 |
|---|---|
| `GET /api/alerts` | 목록(`AlertItem`, `read` 포함). 필터 `status` `type` `origin` + **`unread=true`**(내가 읽지 않은 것) **`important=true`**(확인 필요 이상) + `limit` `cursor` |
| `GET /api/alerts/unread-count` | `{ unread, unreadImportant }` — 처리 상태와 상관없이 내가 읽지 않은 수 |
| `POST /api/alerts/:id/read` | 읽음 표시. 이미 읽었으면 그대로(멱등). 처리 상태는 바꾸지 않음 |
| `POST /api/alerts/read-all` | 모두 읽음. `{ updated }`(이번에 새로 읽은 수). 처리 상태는 바꾸지 않음 |
| `GET /api/alerts/:id` | 상세(`read` 포함) |

- 읽음은 **보호자별**(`AlertRead`: alertId + guardianId)입니다. 한 보호자가 읽어도 다른 보호자의 읽지 않은 수는 그대로입니다. 다른 가구의 알림은 읽을 수 없습니다(404).
- 마이그레이션 `20261117120000_alert_read`: 이미 **종료된** 과거 알림은 읽은 것으로 시작하고, 진행 중인 알림은 읽지 않은 상태로 둡니다.
- 실시간 `alert.read`(`{ alertIds, all }`)는 **같은 보호자의 화면(기기)에만** 가고, 바뀐 것이 없으면(이미 읽음) 보내지 않습니다.

## 화면 (`apps/web/src/features/notifications`)

1. **읽지 않은 알림 수**와 중요 알림 수(`UnreadSummary`) — 수를 불러오지 못하면 0이 아니라 "확인하지 못했습니다". 헤더의 알림 센터 버튼도 같은 수를 보여 주고, 중요한 알림이 읽지 않은 채 있으면 붉은색입니다.
2. **보기**: 전체 / 읽지 않음(수 표시) / 중요 + 알림 종류·처리 상태. 조건은 주소(`?view=unread&type=…&status=…`)에 담겨 새로고침·링크 공유로 같은 목록이 열립니다.
3. **알림 목록**(`AlertCard`): 읽지 않음/읽음 · 중요도 · 처리 상태 · 유형 · 내용 · 시각 · 센서 · 전달 상태 · [읽음으로 표시] · [관련 움직임 기록 보기]. 30건씩 "더 보기".
4. **알림 상세**: 읽음 표시(+ "읽어도 해결된 것은 아닙니다" 안내), 처리(확인·종료), 근거 신호, **채널별 전달 상태와 한계 설명**, 관련 움직임 기록 보기.
5. **모두 읽음**: 확인 대화상자가 "처리 상태도 그대로입니다"를 알립니다. 실패하면 이전 상태로 되돌리고 원인을 알립니다.
6. **개별 읽음**: 화면에 바로 반영하고(낙관적 갱신), 실패하면 되돌립니다.
7. **관련 움직임 기록으로 이동**: `/events?event=<id>&from=<알림이 생긴 날>&to=<같은 날>` — 그 기록의 상세를 엽니다. 움직임 알림은 가장 최근 근거 신호, 센서 알림은 센서 상태 기록으로 이어집니다.

## 실시간 동작 (`hooks/useRealtimeSync.ts`, `lib/alertCache.ts`)

- `alert.created` / `alert.updated`가 오면 **도착한 알림을 목록 캐시에 ID 기준으로 먼저 반영**합니다.
  - 이미 있으면 같은 자리에서 내용만 바꾸고(**읽음 여부는 유지**), 조건에서 벗어나면 뺍니다(진행 중 보기에서 종료됨).
  - 없고 조건에 맞는 새 알림이면 맨 위에 넣습니다. **같은 ID는 한 번만** 들어가고, 이미 센 알림은 읽지 않은 수에 다시 더하지 않습니다. 보기 조건(예: 중요)에 맞지 않는 알림은 넣지 않습니다.
  - 그 뒤 서버에서 다시 읽어 값을 맞춥니다. (캐시 반영은 서버보다 앞서 가는 임시 값)
- `alert.read`(다른 기기에서 읽음 처리) → 목록과 읽지 않은 수를 다시 읽습니다.
- **연결이 끊겼다 복구되면** `connect` 신호에서 목록·읽지 않은 수를 API로 다시 읽어 **놓친 알림을 보충**합니다. 끊겨 있는 동안에는 맨 위 안내가 "최신 정보가 아닐 수 있다"고 알리고, 헤더의 알림 수는 숫자 대신 경고 표시입니다.

## 상태

불러오는 중 · 목록 · 비어 있음(전체 / 읽지 않음 / 중요 / 조건에 맞는 것 없음 — 안내가 다르고, "없다고 모두 확인한 것은 아님"을 밝힘) · 불러오기 실패(다시 시도, 실패를 "알림 없음"으로 보이지 않음) · 다음 쪽 실패(이미 본 알림 유지) · 연결 끊김(받은 알림이 없으면 연결 문제라고 알림) · 읽지 않은 수 실패.

## 한계

- 읽음 표시는 사용자가 직접 합니다. 알림 상세를 열어도 자동으로 읽음이 되지 않습니다. (열기만 한 것과 읽은 것을 구분)
- 이미 `alert.notify`로 화면에 뜬 배너·소리는 읽음과 무관합니다.
- 센서 알림과 센서 상태 기록의 연결은 앞뒤 2분 근접 기준이고, 이미 열려 있던 알림에 합쳐진 상태 변화는 연결되지 않을 수 있습니다.
- 푸시·문자 등 외부 채널의 실제 기기 수신 여부는 확인할 수 없습니다. 수신 확인(전달 영수증)을 받는 채널은 구현하지 않았습니다.
- 알림 유형 "시스템 오류"는 알림 전달 실패 하나뿐입니다.
- 읽음 데이터는 알림을 삭제하는 보관 정책(종료된 알림 정리)과 함께 지워집니다.
