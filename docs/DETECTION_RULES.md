# 움직임 판단 규칙

센서의 움직임 신호에서 **일반 움직임**과 **보호자가 확인하면 좋을 상황(주의 이벤트)** 을 구분하는 엔진의 규칙입니다. 코드는 [`apps/server/src/domain/rules/`](../apps/server/src/domain/rules/) 의 **순수 함수**이고(Express·DB·시계와 분리), 같은 입력과 설정이면 언제나 같은 결과가 나옵니다.

> **이 엔진은 의료기기가 아니며 낙상·사고·외출·실종을 판정하지 않습니다.**
> 센서 하나의 움직임 신호와 설치 위치·시간대에 따른 **추정**일 뿐입니다. 하드웨어와 실험 데이터로 검증되지 않았으므로 **정확도(%)나 확률을 표시하지 않습니다.** 알림이 없다고 괜찮다는 뜻이 아니고, 알림이 있다고 위험이 확정된 것도 아닙니다. (문구 기준: [COPY_GUIDE.md](COPY_GUIDE.md), `FORBIDDEN_PHRASES` 테스트)

## 구조

```
신호 수신(POST /api/ingest/v1/events)
  → 검증(형식·시각·중복 eventId·센서 사용 여부)            services/ingest.service.ts
  → ① 분류 classifyMovementEvent  → DB 에 eventClass 로 저장  domain/rules/classify.ts
  → ② 규칙 평가 evaluateMovementRules → 알림 후보            domain/rules/movement-rules.ts
  → ③ 알림 생성·합치기(cooldown) AlertService.raise          services/alert.service.ts
  → Socket.IO 전달 → 화면 갱신
센서 상태(끊김·복구·배터리)                                 domain/rules/sensor-rules.ts (RULE 5)
```

- ①②는 입력만으로 결과가 정해지는 순수 함수입니다. ③만 DB(기존 알림)를 봅니다.
- "모니터링 시간"은 **모니터링이 켜져 있고, 설정한 야간 시간대이며, 그 야간이 시작된 요일이 일정에 든 시각**입니다(`domain/time.ts#isMonitoredTime`). 자정을 넘는 구간(22:00~06:00)은 시작된 날의 일정을 따르고, 시작 시각은 포함·종료 시각은 제외합니다. **신호가 발생한 시각**으로 판단하므로 늦게 도착한 신호도 발생 시각 기준입니다.

## ① 분류 (RULE 1~3)

| 규칙 | 조건 | 분류(`eventClass`) | 뜻 |
|---|---|---|---|
| RULE 1 | 모니터링 시간 + **침대 주변** 센서 | `BED_EXIT_CANDIDATE` | 침대를 벗어났을 **가능성**을 나타내는 추정. 확정이 아님 |
| RULE 2 | 모니터링 시간 + **현관** 센서 | `ENTRANCE_ACTIVITY` | 현관 쪽 움직임. 외출·실종을 뜻하지 않음 |
| RULE 3 | 그 밖: 이동 경로, 또는 모니터링 시간 밖 | `MOTION_DETECTED` | 일반 움직임. 기록만 함 |

- 분류는 **신호를 받을 때** 정해 DB(`MovementEvent.eventClass`)에 저장합니다. 이후 설정을 바꿔도 과거 기록의 분류는 바뀌지 않습니다. 움직임 기록 화면의 유형·필터가 이 값을 씁니다(이름은 화면에서 "침대 주변 움직임 (추정)" 등으로 표시).
- 분류가 `BED_EXIT_CANDIDATE`여도 **알림은 민감도 규칙을 따로 거칩니다**(아래). 분류는 "무엇으로 보이는 신호인가", 알림은 "보호자에게 알릴 만한가"입니다.
- 알림 후보 여부(`alertEligible`): 모니터링 시간이어야 하고 센서가 **사용** 중이어야 합니다. 아니면 분류는 남기되 알림 후보가 아닙니다(`ineligibleReason`: `NOT_MONITORED_TIME`·`SENSOR_DISABLED`).
- 끊겨 있다가 돌아온 센서의 신호에는 "끊겨 있던 동안의 움직임은 기록되지 않았을 수 있습니다"라는 주의 사항이 붙습니다(`notes`). 분류·알림 여부는 그대로입니다.

## ② 알림 후보 (모니터링 시간의 신호만)

| 알림 유형 | 조건 | 심각도 | 민감도 |
|---|---|---|---|
| `ENTRANCE_APPROACH` | 현관 센서의 신호. 직전 시간 창 안에 침대 주변·이동 경로 신호가 있었다면 문구와 근거에 덧붙임 | 즉시 확인 권장(URGENT) | 모든 민감도 |
| `BED_AREA_ACTIVITY` | 침대 주변 센서의 신호 | 확인 필요(NOTICE) | **높음**일 때만 |
| `BED_TO_PATH` | 이동 경로 신호 + 직전 시간 창(기본 10분) 안에 침대 주변 신호 | 확인 필요 | **보통 이상** |
| `REPEATED_MOVEMENT` | 30분 안에 구역이 바뀐 횟수가 기준 이상. **직전 신호와 15초 이상 떨어져 바뀐 경우만 센다** | 확인 필요 | 기준: 낮음 6 · 보통 4 · 높음 3번 |

- **흐름 판단에는 쓸 수 있는 신호만 씁니다.** 침대→이동 경로, 구역 전환 횟수, 현관 직전 움직임은 **사용 중인 센서의, 모니터링 시간에 발생한 신호만** 봅니다. (이전에는 꺼 둔 센서의 신호와 야간이 시작되기 전의 신호도 섞일 수 있었습니다. 특히 최근 신호를 모두 "지금 신호를 보낸 센서"의 사용 여부로 처리하던 버그를 고쳤습니다.)
- **구역 전환 간격(`REPEATED_MIN_GAP_SECONDS`=15초):** 이웃한 두 센서의 감지 범위가 겹쳐 몇 초 사이로 번갈아 반응하는 것은 사람이 오간 것이 아니라 한 번의 움직임에 대한 겹친 반응일 수 있어 세지 않습니다. **한계:** 구역 사이를 정말 15초 안에 오가는 아주 좁은 집은 이 규칙으로 세지 못합니다(침대→이동 경로 규칙은 그대로 동작). 15초는 현장 데이터로 맞춘 값이 아니라 시뮬레이터 시나리오(30초 간격)와 겹침 잡음 가정에서 정한 초기값입니다.
- **현관 알림의 흐름 정보:** 현관 신호 직전 시간 창(기본 10분) 안에 침대 주변·이동 경로 신호가 있었다면 "직전 10분 안에 침대 주변·이동 경로 구역에서도 움직임 신호가 있었습니다"를 덧붙이고 근거 기록에 담습니다. 심각도(긴급)는 그대로이고 외출·이동 방향을 단정하지 않습니다.
- 민감도는 **센서별 설정이 있으면 그 센서의 신호에는 센서 값이, 없으면 가구 기본값**이 적용됩니다.
- 이동 경로 신호 하나만으로는 알림이 없습니다(RULE 3, 시나리오 4).
- 같은 신호 묶음 안의 같은 종류 후보는 하나로 합쳐집니다. 반복 이벤트는 기존 알림에 합쳐 **횟수(occurrences)** 로 요약됩니다(RULE 4).
- 사용자가 끈 알림 종류(`AlertPreferences`)는 후보가 있어도 만들지 않습니다([SETTINGS.md](SETTINGS.md)).

## ③ 알림 중복 방지 (cooldown)

- 같은 알림 키(`dedupeKey`)의 열린(미종료) 알림이 있고 **마지막 신호가 cooldown(기본 10분, 설정 1~120분) 안**이면 새 알림 없이 기존 알림에 합칩니다. 합칠 때 심각도가 올라가면 **승격(ESCALATED)** 으로 다시 알립니다.
- 키는 **센서별·유형별**입니다: `ENTRANCE_APPROACH:<센서ID>`, `BED_AREA_ACTIVITY:<센서ID>`, `BED_TO_PATH:<이동 경로 센서ID>`. 다른 센서의 같은 유형은 서로의 cooldown에 가려지지 않습니다. (`REPEATED_MOVEMENT`은 여러 센서에 걸쳐 가구 단위)
- **중요한 새 이벤트를 무조건 무시하지 않습니다.** 유형이 다르면 키가 달라 cooldown에 걸리지 않고(예: 침대 주변 알림 cooldown 중에도 현관 알림은 만들어짐), 보호자가 알림을 **종료**하면 cooldown 안이어도 다음 신호는 새 알림이 되며, cooldown이 지나면 새 알림이 만들어집니다.
- 서로 다른 시뮬레이션/실제 출처의 알림은 합치지 않습니다.
- **중복 eventId**: 같은 이벤트 ID는 센서별로 한 번만 저장됩니다(동시에 여러 번 보내도). 중복 전송은 `DUPLICATE`로 응답하고 알림 횟수에도 세지 않습니다.

## RULE 5 센서 문제 (별도 시스템 알림)

| 상황 | 알림 | 비고 |
|---|---|---|
| 신호가 설정한 시간(기본 5분) 동안 없음 | `SENSOR_OFFLINE` | 그 구역의 유일한 활성 센서면 긴급, 아니면 주의. 상태가 풀리면 자동 종료 |
| 끊겼던 센서가 신호를 다시 보냄 | `SENSOR_RESTORED` | 참고(정보). 처음 연결은 복구가 아님 |
| 배터리 부족(기본 20%)·위급(10%) | `LOW_BATTERY` | 참고 / 주의 |
| 알림 전달을 모두 실패 | `DELIVERY_FAILED` | 끌 수 없음 |

**비활성(사용 안 함) 센서**는 신호를 받지 않습니다(수집 API가 403). 따라서 저장도 알림도 없고, 연결 끊김 점검 대상에서도 빠집니다.

## 판단에 쓰는 입력

| 입력 | 출처 |
|---|---|
| 센서 ID·설치 위치(구역) | 등록된 센서 (장치가 보내지 않음) |
| 이벤트 ID·발생 시각·감지 유형 | 장치가 보낸 신호 (`eventId`·`occurredAt`·`type`) |
| 센서 사용 여부·연결 상태 | 센서 정보·마지막 신호 시각 |
| 감지 시간·요일·모니터링 사용 | 감지 설정 |
| 민감도·반복 감지 처리 시간·cooldown | 감지 설정(+센서별 민감도) |
| 알림 종류 켜짐 | 받을 알림 설정 |

| # | 시나리오 | 확인 내용 |
|---|---|---|

| 2 | 야간 침대 주변 감지 | `BED_EXIT_CANDIDATE`로 분류. 알림은 민감도 높음에서만, 문구에 확정 표현 없음 |
| 3 | 야간 현관 감지 | `ENTRANCE_ACTIVITY`, 모든 민감도에서 즉시 확인 권장. 외출·실종을 단정하지 않음 |
| 4 | 일반 이동 경로 감지 | 알림 후보 없음, 일반 움직임으로 기록 |
| 5 | 반복 감지 | 구역 전환 횟수가 민감도 기준에 이르면 후보, 근거 신호를 모두 담고 하나로 합침 |
| 6 | 중복 eventId | 순차·동시 전송 모두 한 번만 저장, 알림 하나, 횟수에 중복 불포함 |
| 7 | cooldown 중 감지 | 센서별로 합쳐짐, 시간이 지나면 새 알림, 다른 센서·다른 유형·종료 후에는 무시되지 않음 |
| 8 | 연결 끊긴 센서 | 끊김 알림 → 신호 재개 시 평소처럼 판단 + 복구 알림, 끊김 알림 자동 종료 |
| 9 | 비활성 센서 | 403, 저장·알림 없음 (엔진 단에서도 후보 아님) |
| 10 | 자정을 지나는 일정 | 자정 전후 모두 야간, 종료 시각 제외, 요일은 야간이 시작된 날 기준 |

## 한계

- 단일 움직임 센서(적외선 등)의 신호이므로 사람·반려동물·열 변화를 구분하지 못하고, 놓치는 움직임이 있을 수 있습니다.
- 규칙의 기준값(민감도별 횟수·시간 창)은 **초기값**이며 실제 환경과 실험 데이터로 검증·조정되지 않았습니다.
- 분류는 받을 때의 설정으로 정해집니다. 설정을 바꿔도 과거 분류를 다시 계산하지 않습니다.
- 알림 문구는 "감지되었습니다 + 확인해 주세요"까지만 말합니다.
