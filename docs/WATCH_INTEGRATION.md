# 스마트워치 알림 연동

> **현재 상태: 스마트워치로는 알림이 전달되지 않습니다.** 네이티브 앱(iPhone·Android)이 없고, 이 서버에는 APNs·FCM 전송도 구현되어 있지 않습니다. 이 문서의 코드는 **채널 구조와 "지원하지 않음"을 사실대로 보고하는 자리**까지만 만들었고, 스마트워치 기기로는 한 번도 시험하지 못했습니다.

## 먼저 알아둘 제약

웹사이트(서버)가 알림을 보낸다고 해서 모든 스마트워치에 전달되는 것은 **아닙니다.** 워치는 보통 **연결된 휴대폰의 알림을 미러링**해서 보여 주며, 아래에 따라 동작이 달라집니다.

- 워치 기종·운영체제 버전, 연결된 휴대폰의 종류
- 휴대폰의 알림 설정(앱별 허용 여부, 방해 금지 모드, 집중 모드)
- 워치 설정(알림 미러링을 켰는지, 손목에 착용·잠금 해제되어 있는지, 휴대폰 화면이 꺼져 있을 때만 미러링되는지 등)
- 휴대폰과 워치의 연결 상태(블루투스/Wi-Fi 등)

따라서 **"서버가 푸시를 보냈다 = 워치에 떴다"가 아닙니다.** 서버는 푸시 서비스가 요청을 받았는지까지만 알 수 있고, 기기에 도착했는지·워치에 미러링됐는지는 알 수 없습니다. (이 프로젝트가 브라우저 푸시를 "전달 확인 불가"로 표시하는 것과 같은 원칙입니다 — [NOTIFICATIONS.md](NOTIFICATIONS.md))

## 현재 구현된 것 / 아닌 것

| 항목 | 상태 |
|---|---|
| 채널 공통 인터페이스 `NotificationChannelAdapter` (`channel`, `external`, `mode()`, `send()`, `sendTest()`, `support?()`) | **구현됨** (앱 화면·브라우저 푸시가 이미 사용 중) |
| 채널별 분리 구현: `InAppAdapter`, `WebPushAdapter`, `WatchNotificationAdapter`(추후 연동용), 미연동 `UnconfiguredAdapter`(문자·카카오) | **구현됨** (`apps/server/src/integrations/notifications/`) |
| DB의 채널·전송 상태 연결: `Channel` 에 `WATCH` 추가, 알림마다 보호자 × 채널로 `NotificationDelivery` 기록 | **구현됨** — 스마트워치는 항상 `NOT_CONFIGURED`("연동되지 않음")로 기록되고, 성공·전달로 세지 않음 |
| 알림 요청 생성·채널별 전송·결과 기록·실패 기록·재시도 | **구현됨** (공통 `NotificationService`: 보호자별·채널별 최대 3회, 30초·2분 간격) |
| 재시도 가능 여부 판단 | **구현됨(이번 추가)**: `DeliveryError.retryable`. 구독 없음·구독 만료·연동 안 됨은 **다시 보내도 같은 결과**라 재시도 없이 바로 실패로 확정, 네트워크·푸시 서비스 오류는 재시도 |
| 사용자별 알림 설정 적용 | **구현됨** — 알림 종류별 수신 설정은 `AlertPreferences`(설정 → 알림)로 알림을 만들지 여부를 정함. **채널별(워치만 끄기 등) 설정은 아직 없음** |
| 지원 여부 확인용 상태 | **구현됨** — `GET /api/system/channel-support` (채널별 `implemented`/`note`, 워치 플랫폼별 `requires`), `GET /api/system/integrations` (`WATCH: NOT_CONFIGURED`). 설정 화면의 채널 설명에도 "아직 만들지 않았습니다" 표시 |
| 테스트 인터페이스 | **구현됨** — `sendTest()`(설정의 "테스트 발송"). 워치는 "아직 만들지 않았습니다" 실패를 돌려줌 |
| **스마트워치로 실제 알림 전달** | **미구현** (아래 작업 필요) |
| iPhone 앱·APNs 전송 / Android 앱·FCM 전송 / watchOS·Wear OS 앱 | **미구현** |
| 실제 기기 시험 | **하지 못함** |

## 스마트워치 연동 분석

아래는 일반적으로 알려진 동작과 구조의 정리입니다. **이 프로젝트에서 실제 기기로 확인한 내용이 아니며,** 제조사 정책·OS 버전에 따라 달라질 수 있어 구현 전에 공식 문서로 다시 확인해야 합니다.

### Apple Watch

| 질문 | 정리 |
|---|---|
| iPhone 앱이 필요한가 | **네이티브 알림을 보내려면 필요합니다.** Apple Watch 는 기본적으로 페어링된 iPhone 의 알림을 보여 주므로, 서버가 APNs 로 보낸 알림이 **iPhone 앱의 알림**으로 도착해야 합니다. |
| APNs 와 워치 알림 미러링의 관계 | 서버 → **APNs** → iPhone 앱 알림. 워치는 iPhone 이 **잠겨 있거나 화면이 꺼진 상태**이고 워치를 착용·잠금 해제했을 때 그 알림을 미러링해 보여 주는 것이 일반적입니다. 서버는 워치를 직접 지정하지 않으며 미러링 여부를 알 수 없습니다. |
| watchOS 앱이 필요한 경우 | 단순 알림 미러링에는 **필요하지 않습니다.** 워치에서 **알림의 버튼(예: "확인했습니다")을 처리**하거나, **알림 화면을 직접 꾸미거나**, 워치 단독 사용·컴플리케이션이 필요할 때 watchOS 앱(또는 iPhone 앱에 포함된 워치 확장)이 필요합니다. |
| 웹 푸시는 되는가 | iOS 16.4 이상에서 **홈 화면에 추가한 웹 앱**은 웹 푸시를 받을 수 있습니다(설정 화면도 이 제한을 안내). 그 알림이 워치로 미러링되는지는 위 알림 설정에 따르며 **이 프로젝트에서는 확인하지 못했습니다.** |
| 필요한 것 | Apple Developer Program 계정, APNs 인증 키, iPhone 앱(푸시 권한·기기 토큰 등록), 서버의 APNs 전송 구현 |
| 실제 기기 시험 조건 | **실제 iPhone + 페어링된 Apple Watch**(알림 허용, 미러링 설정 켬, iPhone 잠금 상태에서 확인). 시뮬레이터는 푸시 수신·미러링 동작을 대신 검증하지 못합니다. |

### Wear OS

| 질문 | 정리 |
|---|---|
| Android 앱 또는 Wear OS 앱이 필요한가 | **Android 앱이면 충분한 경우가 많습니다.** Android 폰의 앱이 올린 알림은 연결된 Wear OS 워치로 기본 전달(브리지)되는 것이 일반적입니다. Wear OS 앱은 워치에서 **자체 화면·독립 동작**이 필요할 때만 필요합니다. |
| FCM 연동 방식 | 서버 → **FCM**(Firebase Cloud Messaging) → Android 앱이 메시지를 받아 **알림을 직접 올림** → 워치로 브리지. Firebase 프로젝트와 서버의 FCM 전송 구현, 앱의 FCM 토큰 등록이 필요합니다. |
| 스마트폰 알림 미러링 | 앱별 알림 허용, 폰의 방해 금지·집중 모드, 워치의 "알림 브리지" 설정에 따라 달라집니다. 서버는 알 수 없습니다. |
| 웹 푸시는 되는가 | Android 의 Chrome 이 보여 주는 웹 푸시 알림도 같은 브리지를 탈 수 있으나 **이 프로젝트에서는 확인하지 못했습니다.** |
| 실제 기기 시험 조건 | **실제 Android 폰 + 페어링된 Wear OS 워치**(앱 알림 허용·브리지 켬). 에뮬레이터 쌍은 페어링은 되지만 실제 기기의 미러링 정책을 그대로 재현하지 못합니다. |

## 구현 계획 (플랫폼별)

| 단계 | 내용 | 필요한 것 |
|---|---|---|
| 0. 지금 | 채널 구조·전달 기록·지원 상태·문서 | (완료) |
| 1. 브라우저 푸시로 먼저 확인 | 이미 구현된 웹 푸시를 **휴대폰 브라우저(Android Chrome / iOS 홈 화면 웹앱)** 에 등록하고, 휴대폰의 알림이 워치에 미러링되는지 **사람이 눈으로 확인** | HTTPS 배포, VAPID 키, 실제 휴대폰·워치. 네이티브 개발 없이 가능성만 확인(결과는 문서에 "확인함/안 됨"으로 기록) |
| 2. Android | Android 앱(FCM 토큰 등록) + 서버 `FcmWatchAdapter`(또는 `Fcm` 채널) | Firebase 프로젝트, Android 앱 개발·서명, 서버 FCM 전송 |
| 3. iOS | iPhone 앱(APNs 토큰 등록) + 서버 APNs 전송 | Apple Developer 계정, APNs 키, iOS 앱 개발 |
| 4. 워치 앱(선택) | 워치에서 "확인했습니다" 처리 등 | watchOS/Wear OS 앱 |
| 공통 | 토큰 등록 API(`/api/push` 와 별도 또는 확장), 만료 토큰 정리, 전달 상태 "확인 불가" 유지, 채널별 수신 설정(워치만 끄기) | |

단계 2·3 은 `WatchNotificationAdapter` 를 같은 인터페이스(`NotificationChannelAdapter`)의 실제 구현으로 **교체**하면 되고, 알림 판단·DB 기록·재시도·화면 표시 코드는 바뀌지 않도록 설계했습니다. 단, 워치용 토큰 저장 테이블은 새로 필요합니다(지금은 없음).

## 시험 방법

- 자동 시험(실제 기기 불필요): `integrations/notifications/watch.adapter.test.ts` — 워치 어댑터가 `NOT_CONFIGURED`·`implemented:false` 를 보고하고, 보내면 **재시도 불가** 실패를 던지며, 알림이 생기면 `WATCH` 전달 기록이 "연동되지 않음"으로 남고 성공으로 세지 않음, `/api/system/channel-support` 가 구현/미구현을 구별함. `web-push.retry.test.ts` — 구독 없음·만료는 재시도하지 않고 일시 오류는 재시도.
- 수동 시험(실제 기기 필요, **아직 안 함**): 위 "실제 기기 시험 조건"에 따라 단계별로 사람이 확인하고 결과를 이 문서에 기록합니다.

## 알려진 한계

- 스마트워치 알림은 **작동하지 않습니다.** 화면에서도 "연동되지 않음"으로 표시됩니다.
- 시뮬레이션으로 만든 알림은 앱 밖으로 나가는 채널(푸시·워치 등)로 보내지 않습니다.
- 알림마다 스마트워치 채널의 "연동되지 않음" 전달 기록이 하나씩 더 남습니다(문자·카카오와 같은 방식). 알림 상세의 채널별 전달 기록에 보입니다.
- 이 문서의 Apple Watch·Wear OS 동작 설명은 일반적인 구조의 정리이며 기기로 검증하지 않았습니다.
