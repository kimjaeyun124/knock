# 움직임 기록 (타임라인)

센서가 감지한 움직임과 센서 상태 변화를 시간순으로 보고, 특정 상황을 찾아보는 화면(`/events`)입니다.

## 기록 데이터 (`TimelineEvent`, `packages/shared/src/timeline.ts`)

| 항목 | 설명 |
|---|---|
| `id` | 이벤트 ID. 움직임 신호는 `mov_…`, 센서 상태 변화는 `sta_…` |
| `sensorId` · `sensorName` | 센서 |
| `eventType` | 이벤트 유형 (아래) |
| `zone` · `origin` | 구역, 실제/시뮬레이션 |
| `occurredAt` · `receivedAt` | 발생·수신 시각 (ISO 8601, UTC). 센서 상태 변화는 서버가 만든 시각이라 둘이 같음 |
| `isLate` | 발생보다 크게 늦게 도착한 신호 |
| `attention` | 주의 수준: `NORMAL`(일반) · `INFO`(참고) · `NOTICE`(확인 필요) · `URGENT`(즉시 확인 권장) |
| `alertRaised` · `alerts[]` | 연결된 알림이 있는가, 그 알림(id·유형·심각도·상태) |
| `description` | 이벤트 설명. 추정 이벤트는 추정이라고 밝힘 |
| `rule` | 판단에 사용된 규칙 `{ text, alertType }` (현재 감지 설정 기준) |

**움직임 신호의 유형은 신호를 받을 때 판단 엔진이 정해 저장합니다**(`MovementEvent.eventClass`, `domain/rules/classify.ts` — [DETECTION_RULES.md](DETECTION_RULES.md)). 설정을 바꿔도 과거 기록의 유형은 바뀌지 않습니다. 주의 수준·알림 연결·설명은 저장하지 않고 원본(신호, 센서 상태 이력, 알림의 근거)에서 그때그때 정합니다. 원본 신호는 바꾸지 않습니다. 설명·규칙 문구는 `apps/server/src/domain/timeline.ts`(순수 함수)에 있습니다.

### 이벤트 유형

| 유형 | 정하는 법 | 화면 이름 |
|---|---|---|
| `BED_EXIT_CANDIDATE` | **모니터링 시간**(켜짐·야간·요일 일정)에 받은 **침대 주변** 센서의 신호 | 침대 주변 움직임 (추정) |
| `MOTION_DETECTED` | 위 두 경우가 아닌 신호: 이동 경로, 또는 모니터링 시간 밖(낮 등) | 일반 움직임 |
| `ENTRANCE_ACTIVITY` | **모니터링 시간**에 받은 **현관** 센서의 신호 | 현관 주변 움직임 (추정) |
| `SENSOR_OFFLINE` | 상태 이력의 "연결 끊김" | 센서 연결 끊김 |
| `SENSOR_RESTORED` | 상태 이력의 "연결됨" (처음 연결 포함 — 설명으로 "처음 연결되었습니다"와 "끊겼던 연결이 복구되었습니다"를 가름) | 센서 연결 복구 |
| `LOW_BATTERY` | 상태 이력의 "배터리 부족·위급" | 배터리 부족 |

**주의:** 침대 주변·현관 관련 유형은 센서 위치와 규칙에 따른 **추정**이며, 움직임 센서 하나의 신호로 낙상이나 외출을 확정하지 않습니다. 화면 문구에도 그렇게 적고, 문구 검사(`FORBIDDEN_PHRASES`)가 서버 설명·규칙 문구와 화면 이름에 걸려 있습니다.

> **요청과 다른 점 — 이름:** 요청하신 `BED_EXIT_CANDIDATE`의 설명 "침대 주변 이탈 추정"의 "이탈"은 이 프로젝트가 금지한 표현(`FORBIDDEN_PHRASES`)이라, 코드 값 `BED_EXIT_CANDIDATE`는 그대로 두고 화면 이름만 "침대 주변 움직임 (추정)"으로 했습니다. 센서 하나의 신호는 침대를 벗어났는지를 알 수 없기 때문입니다.

### 주의 수준

- **움직임 신호:** 연결된 알림 중 가장 높은 심각도. 알림과 연결되지 않으면 `NORMAL`. (알림 하나는 여러 신호를, 신호 하나는 여러 알림을 가질 수 있어 가장 높은 것을 씁니다)
- **센서 상태 변화:** 종류로 정합니다. 연결 끊김·배터리 위급 = 확인 필요, 배터리 부족 = 참고, 연결됨 = 일반. 같은 때 만들어진 알림의 심각도는 `alerts`에 따로 담깁니다.
- 이름은 알림 심각도와 같습니다(참고 / 확인 필요 / 즉시 확인 권장). "주의 이벤트"는 **확인 필요 이상**입니다.

### 알림 연결

- 움직임 신호 → 알림의 근거 연결(`AlertEvidence`)로 정확히 알 수 있습니다.
- 센서 상태 변화 → 연결 기록이 없어, **같은 센서·같은 종류(끊김·복구·배터리)의 알림이 앞뒤 2분 안에 만들어졌는지**로 추정합니다. (알림은 상태 변화와 같은 순간에 만들어지지만, 이미 열려 있던 알림에 합쳐진 경우는 연결되지 않을 수 있습니다)

## API (`apps/server/src/modules/timeline`)

| 요청 | 설명 |
|---|---|
| `GET /api/timeline` | 목록. `from` `to`(ISO) `sensorId` `type` `attention` `alert`(true/false) `order`(desc 기본/asc) `limit`(기본 30, 최대 100) `cursor` |
| `GET /api/timeline/summary` | 같은 조건 전체의 `total` `attention` `alertRaised` `lastEventAt` (한 쪽이 아니라) |
| `GET /api/timeline/:id` | 상세 + 같은 알림의 근거가 된 다른 신호(최대 20건) |

- 두 출처(움직임 신호 SQL / 센서 상태 이력)를 시간순으로 합칩니다. 각 출처에서 `limit+1`건씩 읽어 합치면 앞 `limit+1`건이 그 안에 모두 들어 있어 페이지가 정확하고, 같은 시각이면 ID(`mov_` < `sta_`)로 순서를 정합니다. 양방향(최신순·오래된순) 모두 빠짐·중복 없이 이어 읽는지 테스트합니다.
- 센서 상태 이력은 드물어 한 번에 메모리로 읽어 걸러 냅니다(최대 2000건). 움직임 신호는 DB에서 거릅니다.
- 시각은 서버가 ISO 8601(UTC)로만 처리하고, 날짜 범위 `from`·`to`도 ISO입니다.

## 화면 (`apps/web/src/features/events`)

| 영역 | 파일 |
|---|---|
| 상단: 제목·설명·조회 기간 빠른 선택 (오늘 / 최근 7일 / 최근 30일 / 직접 선택) | `EventsPage.tsx`, `PeriodPicker.tsx` |
| 필터: 날짜 범위·센서·이벤트 종류·주의 수준·알림 발생 여부·정렬·초기화 (좁은 화면에서는 접힘) | `EventFilterPanel.tsx` |
| 요약: 전체 감지 건수·주의 이벤트·최근 감지 시간 (조건 전체 기준) | `EventSummary.tsx` |
| 타임라인: 날짜별 묶음, 아이콘, 시각·종류·위치·설명·배지 ("더 보기"로 30건씩) | `EventTimeline.tsx`, `EventCard.tsx`, `grouping.ts` |
| 상세: 시각·센서(현재 상태)·판단 규칙·알림 처리·관련 신호 | `EventDetailSheet.tsx` |

- **조건은 주소에 담깁니다.** `/events?type=LOW_BATTERY&attention=NOTICE&from=2026-11-01`. 새로고침·뒤로 가기·링크 공유로 같은 목록이, `?event=<id>`로 같은 상세가 열립니다. 올바르지 않은 값은 "전체"로 취급합니다. 조건 변경은 기록에 쌓지 않고, 상세 열기는 쌓아서 뒤로 가기로 닫힙니다.
- **시간대:** 서버는 UTC로 주고, 이 화면은 **기기의 시간대**로 보여 주고 날짜를 나눕니다(`lib/localTime.ts`). 상세에 시간대 이름도 적습니다. 대시보드·알림은 한국 시간 고정이라, 한국 밖에서 보면 두 화면의 시각 표시가 다를 수 있습니다.
- 정렬은 최신순(기본)/오래된순이며 서버가 처리합니다. 조건이 바뀌면 처음부터 다시 읽습니다.
- **상태:** 불러오는 중 · 기록 있음 · 비어 있음(기록 자체가 없음 / 조건에 맞는 것이 없음 — 안내와 다음 행동이 다름) · 불러오기 실패(원인·요청 번호·다시 시도, 실패를 "없음"으로 보이지 않음) · 다음 쪽 실패(이미 본 기록 유지) · 연결 끊김(받아 둔 기록이 있으면 "최신이 아닐 수 있음") · 기간 오류(시작이 종료보다 늦음, 조회하지 않음).
- 실시간 신호(움직임·센서 상태·알림)가 오면 목록·요약을 다시 읽습니다.
- **Mock:** `VITE_MOCK_FEATURES=timeline` — 서버와 같은 조건·정렬·cursor·요약·상세 계약을 메모리에서 흉내 내는 예시 데이터(`(샘플)` 이름, 출처=시뮬레이션). 여섯 유형이 모두 나옵니다.

## 한계

- 센서 상태 이력과 알림의 연결은 시간 근접 추정입니다(위 "알림 연결").
- "관련 센서 상태"는 **현재** 상태이며, 그 기록이 만들어진 때의 상태가 아닙니다(상세에 그렇게 적음). 기록 시점의 센서 상태는 따로 저장하지 않습니다.
- "판단에 사용된 규칙"은 **현재 감지 설정** 기준의 설명입니다. 설정을 바꾸면 과거 기록의 설명도 바뀔 수 있습니다.
- 센서 상태 이벤트의 `receivedAt`은 발생 시각과 같습니다(서버가 만든 시각).
- 처음 연결된 센서와 끊겼다 돌아온 센서는 둘 다 "센서 연결 복구" 유형이지만, 상태 이력의 설명으로 구분해 설명 문장이 다릅니다. 끊겼다 돌아온 경우에만 알림(`SENSOR_RESTORED`, 알림 센터 참고)이 만들어집니다.
- 배터리가 회복된 기록(`BATTERY_OK`)은 요청한 이벤트 유형에 없어 보여 주지 않습니다.
- 주의 수준·유형 필터는 알림이 여럿 연결된 신호를 "가장 높은 수준"에만 속하게 합니다.
