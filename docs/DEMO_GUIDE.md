# 발표 시연 가이드

실제 센서 없이 서비스의 핵심 흐름을 **반복해서** 보여 주기 위한 안내입니다. 시연의 모든 신호는 **실제 서버 처리 경로**를 지납니다.

```
시뮬레이터(서버) ─ HTTP·장치 토큰 ─▶ 수집 API → 검증·중복 제거 → DB 저장 → 감지 규칙 → 알림 생성·전달 → Socket.IO → 화면 갱신
```

화면 버튼이 알림을 직접 만들지 않습니다. 버튼 → 서버 → 수집 API → DB → 규칙 → 알림 순서이고, 화면의 "전송 결과"는 서버의 응답입니다. ([SIMULATOR.md](SIMULATOR.md))

> **발표에서 꼭 말할 것:** 이 시연의 센서는 **시뮬레이션**이며 실제 하드웨어가 아닙니다. 이 서비스는 낙상·실종을 판정하지 않고, 센서의 움직임 신호를 알려 주는 보조 도구입니다.

## 1. 준비 (한 번만)

```bash
npm install
cp .env.example .env          # SEED_DEMO_PASSWORD 를 12자 이상으로 바꿉니다
npm run db:deploy             # DB 만들기·마이그레이션
npm run db:seed               # 데모 가구·보호자·샘플 센서 3개·샘플 움직임 기록 (여러 번 실행해도 같은 결과)
npm run dev                   # 서버(4000)와 웹(5173) 실행
```

- 접속: <http://localhost:5173> — 로그인 `demo@example.com` / `.env` 의 `SEED_DEMO_PASSWORD`
- 시뮬레이터는 **개발 환경에서 기본으로 켜집니다.** 운영(`NODE_ENV=production`)에서는 꺼지고 화면·API 가 없습니다. 시연은 개발 환경(자기 노트북)에서 하세요.
- 데모 보호자·보호 대상은 가상이며 실제 개인정보가 없습니다. (보호 대상 호칭 "어르신(데모)")

### 준비되는 것

| 요구 | 준비 방법 |
|---|---|
| 테스트용 보호자 계정 | `npm run db:seed` → `demo@example.com` |
| 테스트용 보호 대상 | 시드가 "어르신(데모)" 생성 |
| 침대 주변·이동 경로·현관 센서, 정상 상태 | **센서 시뮬레이터** 화면의 "시뮬레이션 센서 만들기"(또는 `demo reset`)가 세 구역의 시뮬레이션 센서를 만들고 첫 신호를 보냄 → 세 센서 모두 "연결됨" |
| 알림 설정 | 시드의 기본값(보통 민감도, 야간 22:00~06:00, 알림 4종 켜짐). 설정 → 감지·알림에서 확인 |
| 샘플 움직임 기록 | 시드가 최근 사흘 밤의 기록 9건을 만듦. (**`demo reset` 은 시뮬레이션 데이터를 지우므로 이 샘플 기록도 지워집니다.** 그때는 시나리오를 한 번 재생해 기록을 쌓으세요.) |

### 야간 시간 맞추기 (중요)

감지 규칙은 **모니터링 시간(기본 밤 10시~아침 6시)에 일어난 신호에만 알림**을 만듭니다. 낮에 발표하면 움직임은 **기록만 되고 알림은 만들어지지 않습니다.** 둘 중 하나를 하세요.

- **(권장) 설정 → 감지 시간·민감도**에서 모니터링 시간을 발표 시간대가 들어가게 바꿉니다. (예: 시작 00:00, 종료 23:59) 끝나면 되돌립니다.
- 또는 시뮬레이터의 "전송 방식" 옆 **"가장 최근의 야간 시간으로 보내기"** 를 씁니다. 신호의 발생 시각을 과거의 야간으로 실어 보내며, 서버는 "늦게 도착한 신호"로 표시하되 그 시각으로 규칙을 판단합니다.

시뮬레이터 화면과 `npm run sim -- demo status` 모두 "지금이 야간 시간대인지"를 알려 줍니다.

## 2. 데모 모드 표시와 안전장치

- 시뮬레이션 데이터가 서버에 있으면 **모든 화면 위에 "시연용 시뮬레이션 데이터가 있습니다. … 실제 센서나 실제 상황이 아닙니다."** 띠가 뜹니다. (설정 → 데이터 관리로 이동하는 링크 포함)
- 센서·기록·알림에는 **"시뮬레이션"** 표시가 붙고, 실제 센서의 신호와 섞어 판단하지 않습니다.
- 시뮬레이션으로 만든 알림은 **앱 밖으로 나가는 채널(푸시 등)로 보내지 않습니다.**
- **초기화는 시뮬레이션 데이터만 지웁니다.** 실제 센서·기록·알림은 건드리지 않습니다(자동 시험으로 확인). `demo reset` 은 끝나면 "실제 데이터(건드리지 않음): 센서 N, 기록 N, 알림 N"을 보여 줍니다.
- 개발 전용 기능(시뮬레이터 화면·API·`/api/dev/*`)은 운영에서 꺼져 있으면 경로 자체가 없습니다. 모든 시뮬레이터 API 는 로그인한 보호자만, 자신의 가구에만 쓸 수 있습니다.

## 3. 시연 전 초기화 (반복 시연)

```bash
export TETRIS_EMAIL=demo@example.com
export TETRIS_PASSWORD='<SEED_DEMO_PASSWORD 값>'   # 셸 기록에 남기지 않으려면 환경변수로만 전달
npm run sim -- demo reset     # 시뮬레이션 데이터 삭제 → 세 구역 시뮬레이션 센서 새로 연결
npm run sim -- demo status    # 상태 확인 (아무것도 바꾸지 않음)
```

화면에서 하려면 **설정 → 데이터 관리 → 시뮬레이션 데이터 삭제**, 그 뒤 **센서 시뮬레이터 → "시뮬레이션 센서 만들기"** 입니다. 둘은 같은 서버 기능을 씁니다.

한 번 준비해 두면 아래 시나리오를 **어느 순서로든, 몇 번이든** 재생할 수 있습니다. 시나리오 사이에는 알림을 "확인했습니다"→"알림 종료"로 정리하거나 `demo reset` 을 다시 실행합니다.

## 4. 시나리오별 진행

화면 이름은 실제 화면 기준입니다. 센서 시뮬레이터는 **설정 → 센서 시뮬레이터**(`/dev/simulator`)에 있습니다. 발표에서는 시뮬레이터를 한쪽 창, 대시보드를 다른 창에 나란히 띄우면 **새로고침 없이 바뀌는 것**을 보여 줄 수 있습니다.

### 시나리오 1 — 정상 모니터링

| 순서 | 할 일 | 예상 결과 |
|---|---|---|
| 1 | 대시보드를 연다 | 상태 카드 **"정상"** + "안전을 보장하는 것은 아닙니다" 안내, 센서 요약에 세 구역 센서가 **연결됨(시뮬레이션)** |
| 2 | 모니터링 상태를 확인한다 | "모니터링 켜짐", 현재 야간 시간대 여부 |
| 3 | 연결된 센서를 확인한다 | 센서 관리 → 침대 옆·복도·현관문, 연결·배터리·마지막 통신 시각 |
| 4 | 움직임 기록을 확인한다 | 움직임 기록 화면(샘플 기록 또는 방금 쌓은 기록, 모두 "시뮬레이션") |

### 시나리오 2 — 야간 침대 주변 움직임

| 순서 | 할 일 | 예상 결과 |
|---|---|---|
| 1 | 야간 시간대인지 확인(위 "야간 시간 맞추기") | 시뮬레이터에 "야간 시간대입니다" |
| 2 | 시뮬레이터 시나리오 **"침대 주변에서 이동 경로로 이어진 움직임"** 재생(또는 침대 주변 카드의 "움직임 보내기" → 이동 경로) | "재생 중" 표시, 전송 결과에 **저장됨** |
| 3 | 대시보드를 본다 | **새로고침 없이** 움직임이 나타나고 상태가 **"확인 필요"** 로 바뀜 (민감도 낮음이면 알림 없이 기록만) |
| 4 | 알림 센터를 연다 | "침대 주변에서 이동 경로로 이어진 움직임" 알림 1건, 전달 상태(앱 화면 전달됨, 푸시 등은 "연동되지 않음" 또는 "전달 확인 불가") |

> 침대 주변 **단독** 움직임은 민감도가 "높음"일 때만 알림이 됩니다. 시나리오는 이를 설명하기 좋습니다. 단일 센서로는 침대를 벗어났는지 알 수 없으므로 문구도 "침대 이탈"이 아니라 "움직임"입니다.

### 시나리오 3 — 현관 주변 움직임

| 순서 | 할 일 | 예상 결과 |
|---|---|---|
| 1 | 시뮬레이터에서 현관 카드의 **"움직임 보내기"**(또는 시나리오 "현관 근처 움직임 재생") | 전송 결과 **저장됨**, 새 알림 표시 |
| 2 | 화면 상단 | **"즉시 확인 권장"** 알림 띠(모든 민감도) |
| 3 | 알림에서 **관련 움직임 기록 보기** | 움직임 기록으로 이동해 해당 신호가 열림 |
| 4 | "확인했습니다" → "알림 종료" | 처리 상태가 바뀜. **읽음과 해결은 다르다**는 안내 |

### 시나리오 4 — 센서 연결 끊김

| 순서 | 할 일 | 예상 결과 |
|---|---|---|
| 1 | 시뮬레이터 침대 주변 카드의 **"끊김 바로 확인"** | 서버가 실제 점검 함수를 실행해 연결 끊김을 판단 |
| 2 | 대시보드 | 상태가 **"주의"** 로 바뀌고 이유에 "연결이 끊긴 센서"(또는 구역에 센서가 하나뿐이면 "즉시 확인") |
| 3 | 센서 관리 | 해당 센서 **연결 끊김** 배지, 마지막 통신 시각, 끊긴 센서 N개 요약 |
| 4 | 시뮬레이터 **"연결 복구"** | 센서가 **연결됨**으로, 끊김 알림은 자동 종료, "연결 복구" 정보 알림 |

> **"끊김 바로 확인"은 시간을 건너뛰는 시연용 단축**입니다(마지막 신호 시각을 과거로 돌리고 실제 점검을 바로 실행). 실제 경로 그대로 보이려면 "연결 끊기" 후 기준 시간(기본 5분)을 기다립니다. 발표에서는 이 사실을 말해 주세요.

선택: 배터리 **18%**(부족, 참고)·**9%**(위급, 확인 필요)를 적용하면 같은 수준의 알림이 **한 번만** 생깁니다.

### 시나리오 5 — 불필요한 알림 방지

| 순서 | 할 일 | 예상 결과 |
|---|---|---|
| 1 | 현관 카드에서 **"움직임 보내기"** 를 짧은 간격으로 3~4번 누름(또는 전송 방식 "반복"으로 한 번에) | 전송 결과마다 **저장됨** |
| 2 | 움직임 기록 | 같은 구역의 **기록이 모두** 남음(4건) |
| 3 | 알림 센터 | 현관 알림은 **1건**(반복 억제 시간 10분 안에는 새 알림 대신 근거 신호만 추가) |
| 4 | 말로 설명 | 이벤트 기록은 **센서가 감지한 모든 신호**, 알림은 **보호자를 방해하지 않도록 줄인 것** |
| 5 | (선택) 전송 방식 **"중복"** | 같은 이벤트 ID 를 두 번 보내면 첫 번째 `저장됨`, 두 번째 `중복` — DB 에는 한 건 |

### (선택) 웹캠으로 직접 움직임 보여 주기

버튼 대신 **내가 카메라 앞에서 움직여** 신호를 만드는 장면입니다. 설정 → **웹캠 움직임 감지**에서 "카메라 시작"을 누릅니다. (기본: 화면을 3구역으로 나눔 — 왼쪽 침대 주변·가운데 이동 경로·오른쪽 현관, 낮에는 "야간 시간으로 보내기"가 자동으로 켜짐) **왼쪽에서 뒤척이면 기록만, 오른쪽으로 걸어 나가면 알림**이 뜨고, 대시보드와 알림 센터가 새로고침 없이 바뀝니다. 알림은 이 화면이 열려 있을 때 배너로 뜨며 소리는 헤더의 "알림 소리"를 켜야 납니다. 영상은 브라우저 밖으로 나가지 않고 움직임 신호만 시뮬레이션 센서로 기록됩니다. **조명 변화·흔들림도 움직임으로 보는 단순한 방식**이니 "사람을 인식하는 것이 아니다"라고 말하세요. 자세한 내용과 한계는 [WEBCAM_MOTION.md](WEBCAM_MOTION.md). 리허설에서 카메라 위치와 민감도를 먼저 맞춰 두세요.

## 5. 명령줄로 시연 보조

```bash
npm run sim -- scenarios                    # 시나리오 목록 (서버에 연결하지 않음)
npm run sim -- scenario entrance --speed 60 --wait   # 현관 시나리오를 60배속으로 재생하고 끝날 때까지 기다림
npm run sim -- motion ENTRANCE              # 현관 움직임 한 건
```

(`TETRIS_EMAIL`·`TETRIS_PASSWORD` 필요.) 전달 실패 시나리오는 약 2분 30초가 걸립니다(재시도 간격을 실제 시간으로 기다림).

## 6. 발생 가능한 오류와 발표 중 복구

| 증상 | 원인 | 복구 |
|---|---|---|
| 움직임을 보냈는데 알림이 없음 | 야간 시간대가 아님 / 민감도가 낮음 / 반복 억제 시간(10분) 안 | 모니터링 시간을 바꾸거나 "야간으로 보내기", 민감도 확인, `demo reset` 후 다시 |
| 시뮬레이터 화면이 "꺼져 있습니다" / 명령이 404 | 운영 모드이거나 `SIMULATOR_ENABLED=false` | 개발 모드로 실행(`npm run dev`), `.env` 확인 |
| "수집 API 가 신호를 받지 않았습니다" | 센서가 없거나 사용 안 함, 신호 시각이 너무 오래됨 | "시뮬레이션 센서 만들기"/`demo reset` |
| 센서가 "연결 끊김"인 채로 남음 | "연결 끊기"를 눌렀거나 오래 신호가 없음 | 시뮬레이터 **"연결 복구"** |
| 화면 위에 "연결이 끊겼습니다" 안내 | 서버가 멈췄거나 네트워크 끊김 | 서버 터미널 확인 후 재시작(DB 는 그대로). 화면은 **받아 둔 정보를 지금 상태로 보여 주지 않고** 연결이 돌아오면 자동 복구 |
| 로그인이 안 됨 / 429 | 비밀번호를 잘못 입력(15분에 5회 제한) | 시드 비밀번호 확인, 15분 대기 또는 서버 재시작 |
| 알림 전달 실패 경고가 뜸 | 전달 실패 주입이 켜져 있음 | 시뮬레이터 **"전달 실패 주입 끄기"**(10분 뒤 자동으로 꺼짐) |
| 알림이 너무 많아 정신없음 | 이전 시연의 알림이 남음 | `npm run sim -- demo reset` 또는 설정 → 데이터 관리 |
| 아무것도 안 될 때 | — | 최후 수단: 서버 종료 → `npm run db:deploy && npm run db:seed` → `npm run dev` |

## 7. 자동 시험으로 확인한 것

E2E `e2e/tests/demo.spec.ts`(실제 서버·브라우저): 시뮬레이션 데이터가 있으면 표시 띠가 보이고 지우면 사라짐 / 같은 구역의 반복 신호는 기록 4건·알림 1건 / 시뮬레이션 데이터를 지우고 센서를 다시 연결하면 처음 상태로 돌아가 시나리오를 반복할 수 있음. 나머지 시나리오는 기존 E2E(`flows.spec`, `sensor-health.spec`, `simulator.spec`, `notifications.spec`)가 같은 경로로 확인합니다. CLI `demo reset|status` 는 `packages/simulator` 단위 시험(실제 데이터를 지우는 호출이 없음, 시뮬레이터가 꺼진 서버에서는 실패로 끝남)으로 확인했습니다.

## 8. 한계

- 센서는 시뮬레이션이며 **실제 하드웨어로는 확인하지 않았습니다.** 감지 기준은 시뮬레이터로 맞춘 초기값입니다.
- 푸시·문자·카카오·스마트워치는 시연에서 **전달되지 않습니다.** 앱 화면 알림만 열린 화면에 전달됩니다. (브라우저 푸시는 VAPID 키를 설정하고 기기를 등록하면 보낼 수 있으나, 실제 푸시 서비스로 기기에 도착하는 것까지는 확인하지 못했습니다.)
- `demo reset` 은 시드가 만든 과거 샘플 기록을 지우고 다시 만들지 않습니다. 샘플 기록이 필요하면 새 DB 에서 `db:seed` 를 먼저 하거나 시나리오를 한 번 재생하세요.
- 시뮬레이터의 최근 전송 기록·"신호를 보내지 않는 중" 상태는 메모리에만 있어 서버를 다시 시작하면 사라집니다.
