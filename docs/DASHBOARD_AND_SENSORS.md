# 대시보드와 센서 관리

## 대시보드

### 영역 (위에서 아래, 모바일은 한 줄로)

| 영역 | 내용 | 파일 |
|---|---|---|
| 인사·요약 | 날짜·시간(30초마다 갱신), "안녕하세요. 오늘의 안전 상태를 확인하세요.", 모니터링 켜짐 여부, 마지막 데이터 수신 시각 | `GreetingHeader.tsx` |
| 실시간 안전 상태 카드 | 상태 이름·아이콘·한 줄 설명·마지막 업데이트 시각 | `OverallStatus.tsx`, `deriveOverallStatus.ts` |
| 현재 모니터링 | 시작 시각, 감지 일정, 야간 모니터링 여부, 연결된 센서·정상 작동 센서 수 | `MonitoringCard.tsx` |
| 최근 움직임 | 최신 5건(시각·구역·종류·주의 수준)과 "전체 기록 보기" | `RecentMovements.tsx` |
| 센서 요약 | 침대 주변·이동 경로·현관별 연결 상태와 배터리 | `ZoneSensors.tsx` |
| 최근 7일 움직임 | 날짜별 감지 건수(막대)·주의 이벤트 수·범례·표, 기록이 없으면 빈 상태 | `WeeklySummary.tsx` |
| 빠른 작업 | 센서 관리 · 알림 설정 · 전체 기록 확인 | `QuickActions.tsx` |

초기 설정 미완료·앱 밖 알림 불가 같은 꼭 알아야 할 안내는 상태 카드 바로 아래에 조건부로만 나옵니다.

### 상태 이름 (실제 안전을 보장하는 문구는 쓰지 않음)

| 이름 | 조건 | 문구 |
|---|---|---|
| 정상 | 사용 중인 센서가 모두 연결, 열린 움직임 알림 없음 | "최근 감지된 주의 이벤트가 없습니다" + "센서가 보낸 신호를 기준으로 한 표시이며 안전을 보장하는 것은 아닙니다" |
| 주의 | 알림은 없지만 일부 센서 끊김·배터리 부족·첫 신호 대기·알림 전달 실패 | 이유를 그대로 나열 |
| 확인 필요 | 열린 움직임 알림 있음 (긴급이면 "즉시 확인 권장" 배지를 함께) | 알림 제목 |
| 연결 끊김 | 사용 중인 센서가 모두 끊김, 또는 이 화면이 서버와 연결되지 않음 | "지금의 움직임을 확인할 수 없습니다" |
| 상태 확인 불가 | 정보를 불러오지 못함 | "정상으로 보지 말고 다시 확인해 주세요" |

"안전합니다"·"이상 없음" 등은 `FORBIDDEN_PHRASES` 검사로 막혀 있고, 대시보드 테스트가 화면 전체 글자에서 확인합니다.

**최근 움직임의 "주의 수준":** 움직임 신호 하나에는 위험도가 없습니다. 그래서 "야간 감지 / 주간 감지"만 구분합니다(감지 시각이 야간 모니터링 시간대인가). 알림의 수준(주의·긴급)은 신호들의 흐름을 보고 서버가 따로 정합니다. **7일 요약의 "주의 이벤트"**는 그날 만들어진 움직임 알림(주의·긴급) 수이며, 센서 상태·전달 실패 알림은 세지 않습니다.

**"모니터링 시작"**은 별도 기록이 없어 사용 중인 센서 중 가장 먼저 등록한 시각으로 보여 주고, 그렇다고 화면에 적습니다.

### 화면 상태 5가지

| 상태 | 언제 | 표시 |
|---|---|---|
| Loading | 처음 불러오는 중 | "대시보드를 불러오는 중" + 자리 표시 |
| Success | 불러옴 | 위 일곱 영역 |
| Empty | 센서가 하나도 없음 | "아직 등록된 센서가 없습니다" + 센서 등록·초기 설정 링크. "정상" 카드는 만들지 않음 |
| Error | 처음부터 불러오지 못함 | 원인 + 다시 시도. 받아 둔 정보가 있는데 갱신만 실패하면 상태 카드가 "상태 확인 불가"(+ "마지막으로 확인한 상태")이고 "최신 정보를 불러오지 못했습니다" |
| Offline | 연결이 끊김 | 상태 카드 "연결 끊김"(+ 마지막으로 확인한 상태), 각 카드에 "연결이 끊기기 전에 받은 정보", 받은 정보가 없으면 "연결이 끊겨 대시보드를 볼 수 없습니다" |

### 데이터 흐름

```
DashboardPage ─ useDashboard() ─ api.dashboard.summary()   ← DashboardApi (services/api/types.ts)
                                      │
              ┌───────────────────────┴───────────────────────┐
   실제: services/api/http.ts                     개발용: services/api/mock.ts
   GET /api/v1/dashboard/summary 한 번.            createMockDashboardSummary()
   서버(DashboardService)가 sensors · events        ("(샘플)" 이름, 출처=시뮬레이션, mock:true)
   (최근 5건, 7일 집계) · alerts(진행 중) ·
   settings 를 모아 줌
```

- **타입:** `packages/shared/src/dashboard.ts`의 `DashboardSummary`(Zod). 서버의 `GET /api/v1/dashboard/summary`가 같은 타입으로 응답하고, 웹은 `DashboardSummaryResponseSchema`로 검증합니다. 개수(연결된 센서 수 등)는 담지 않고 원본 목록에서 화면이 계산합니다.
- **서버에 새로 생긴 것:** `GET /api/events/daily?days=7` — 한국 시간 날짜별 움직임 수·시뮬레이션 수·주의 알림 수(빠진 날은 0건). 클라이언트에서 7일치를 페이지로 세면 건수가 조용히 틀어질 수 있어 서버에서 집계합니다.
- **Mock:** `VITE_MOCK_FEATURES=dashboard`. 실제 응답과 같은 `DashboardSummary` 타입이며 `Mocked<>` 표식(`mock: true`)이 붙고, 화면에는 "개발용 샘플 데이터입니다" 안내가 뜹니다. 운영 빌드에는 들어가지 않습니다.
- 실시간 신호(센서·움직임·알림·설정 변경)가 오면 대시보드도 다시 읽고, 놓친 경우를 위해 1분마다도 읽습니다.
- 하나라도 불러오지 못하면 전체를 실패로 다룹니다. (일부만 채운 화면이 "이상 없음"처럼 보이지 않게)

## 센서 관리

### 센서 상태: 연결과 배터리는 독립

| 요구한 이름 | 구현 |
|---|---|
| ONLINE / OFFLINE / UNKNOWN | **연결** 값(`state`): 연결됨 / 연결 끊김 / 첫 신호 대기 중(=UNKNOWN). 사용을 끈 센서는 "사용 안 함" |
| LOW_BATTERY | **배터리** 값(`batteryLevel`): 충분 / 부족 / 위급 / 정보 없음. 연결과 따로 표시되어 "연결됨 + 배터리 부족"도 그대로 표현됩니다 |

`features/sensors/sensorStatus.ts`의 `sensorDisplayStatus`가 한 센서를 ONLINE·LOW_BATTERY·OFFLINE·UNKNOWN·DISABLED 중 하나로 요약하고(요약용), 화면의 배지는 연결·배터리를 각각 따로 보여 줍니다. 배터리 정보가 없으면 퍼센트를 지어내지 않고 "배터리 정보 없음"입니다. 꺼 둔 센서는 연결·배터리 경고를 만들지 않습니다.

### 기능

| 기능 | 구현 |
|---|---|
| 목록 | 이름·위치·유형·사용 여부·연결·배터리·마지막 통신·배터리 경고·"상세 설정" 버튼. 연결 끊김·배터리 부족 센서 수를 목록 위에서 먼저 알림 |
| 상세 | 위 정보 + 펌웨어·등록 시각·최근 신호 10건 |
| 이름·설치 위치 수정 | **저장 실패 시 이전 값으로 복구** — 목록·상세는 바로 반영(낙관적 갱신)했다가 실패하면 되돌리고, 입력칸도 저장 전 값으로 되돌린 뒤 원인과 해결 방법을 알림. 바뀐 게 없으면 저장 버튼이 꺼져 있음 |
| 사용/비사용 | 스위치. **끌 때만** 확인 대화상자(모니터링에서 빠지므로), 켤 때는 바로. 실패하면 되돌림 |
| 연결 상태 확인 | 상태를 다시 읽어 확인 시각과 결과를 알림. **센서에 직접 신호를 보내는 것이 아니라 서버가 마지막으로 받은 신호 기준**이라고 화면에 밝힘 |
| 연결 해제 | 확인 대화상자 → (켜져 있으면 먼저 끄고) 센서 삭제. **센서와 움직임 기록이 영구 삭제되며 되돌릴 수 없다**고 알림. 중간에 실패하면 어디까지 되었는지 알림 |
| 토큰 재발급 | 확인 대화상자 → 새 토큰을 한 번만 표시 |
| 오류 | 서버 메시지를 그대로 던지지 않고 **원인 + 해결 방법**으로 알림 (`sensorErrors.ts`: 네트워크·검증·로그인 만료·없는 센서·개수 제한·요청 과다·서버 문제) |
| 로딩 | 저장·등록·확인·해제 중에는 버튼이 "…하는 중"으로 바뀌고 다시 눌러도 중복 요청이 가지 않음 |

### 등록 흐름 (5단계)

1. **센서 유형** — 지원하는 유형은 "움직임 감지 센서" 하나입니다.
2. **연결 방식** — ① 장치 토큰(실제 센서) ② 시뮬레이션 센서(개발·시연용, 서버에서 시뮬레이터가 켜져 있을 때만) ③ 블루투스·지그비 직접 연결(**지원하지 않음**, 이유와 함께 선택 불가로 표시)
3. **이름과 설치 위치** — 구역을 고르면 기본 이름이 채워지고, 직접 고친 이름은 덮어쓰지 않음
4. **장치 연결** — 내용 확인 → 등록 → 장치 토큰을 **한 번만** 표시(저장소·주소에 남기지 않음). 등록 뒤에는 이전 단계로 돌아갈 수 없음
5. **연결 확인** — 3초마다 센서 상태를 읽어 첫 신호가 오면 "연결되었습니다". 오지 않으면 해결 방법(토큰 확인·전원·네트워크·움직여 보기)을 안내하고 "나중에 확인하고 마치기" 가능

**시뮬레이션 분리:** 2단계에서 시뮬레이션을 고르면 3단계로 줄고(실제 장치용 단계 없음) "실제 장치가 아닙니다"를 분명히 알립니다. 만들어진 센서는 모든 화면에서 "시뮬레이션"으로 표시됩니다. 실제 장치와 같은 방식으로 등록되는 가상의 센서는 없습니다.

### 구조

센서 UI·훅·상태 모델·오류 해석·등록 정의는 `apps/web/src/features/sensors/`에 있습니다(`SensorsPage` `SensorDetailPage` `RegistrationWizard` `hooks.ts` `sensorStatus.ts` `sensorErrors.ts` `registration.ts`). **API 서비스와 타입은 프로젝트 전체가 쓰는 `services/api`(`SensorsApi`)와 `packages/shared`(`Sensor` 등 Zod 스키마)에 있고 feature 안으로 옮기지 않았습니다.** 서버가 이미 센서 API를 제공하므로 실제 API를 씁니다. Mock이 필요할 때는 `VITE_MOCK_FEATURES=sensors`로 메모리 속 Mock(`createMockSensorsApi`, 서버와 같은 개수 제한·"사용 안 함 후 삭제" 규칙, 새로고침하면 초기화)을 쓸 수 있습니다. 이때 대시보드는 별도(`dashboard`)로 골라야 합니다.

### 하지 않은 것

- **설치 위치를 자유 입력으로 받지 않습니다.** 위치는 침대 주변·이동 경로·현관 세 구역 중 선택입니다. 규칙 엔진이 구역의 순서(침대 → 이동 경로 → 현관)로 알림을 만들기 때문에 임의 문자열을 받으면 규칙이 동작하지 않습니다. 이름은 자유롭게 정할 수 있습니다.
- **센서 유형은 움직임 감지 하나**, 직접 무선 연결(블루투스·지그비)은 지원하지 않습니다. 센서 ID 입력 단계도 없습니다. 식별은 발급되는 장치 토큰이 합니다.
- **연결 확인은 센서에 직접 신호를 보내지 않습니다.** 서버가 받은 마지막 신호를 기준으로 합니다.
