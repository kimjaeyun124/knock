# 실제 센서 연결 (하드웨어 연동 구조)

> **현재 상태: 실제 하드웨어는 연결되어 있지 않습니다.** 센서 모델·제조사·통신 프로토콜이 확정되지 않아, 이 문서와 코드는 **하드웨어가 정해졌을 때 끼워 넣을 구조와 시험 가능한 부분**까지만 다룹니다. 특정 제조사 SDK나 장치가 있다고 가정하지 않았고, 실제 센서로는 한 번도 시험하지 못했습니다.

## 구조

```
 시뮬레이터 ──┐                                         ┌─ 센서 식별(장치 번호) ─ 출처 확인 ─ 사용 중인지 확인
 (실제 센서   ├─▶ SensorAdapter ─▶ 표준 이벤트 ─▶ SensorEventGateway ─▶ 중복 제거 ─▶ IngestService
  하드웨어)  ──┘   연결·재연결·정규화    (검증됨)                                       │
                                                                  저장 → 감지 규칙 → 알림 → 실시간 화면
 HTTP 수집 API (/api/ingest/v1, 이미 동작) ───────────────────────────────────────────▶ IngestService
```

- **어댑터는 통신만** 합니다(연결·재연결·장치별 형식 읽기). 감지 규칙·알림 판단은 하지 않습니다. 그래서 시뮬레이터든 실제 센서든 **같은 `IngestService`** 를 지나 같은 저장·규칙·알림 경로를 탑니다.
- 이미 동작하는 **HTTP 수집 API**([INGEST_CONTRACT.md](INGEST_CONTRACT.md))도 같은 `IngestService` 를 씁니다. 지금 시뮬레이터 화면은 이 HTTP 경로로 신호를 보냅니다.
- 코드: `apps/server/src/integrations/sensors/`, 표준 이벤트 계약: `packages/shared/src/sensor-events.ts`.

### SensorAdapter (`types.ts`)

| 메서드 | 책임 |
|---|---|
| `connect()` / `disconnect()` | 장치(또는 브로커)와 연결·해제. 실패하면 던지고 상태가 `FAILED` |
| `reconnect()` | 끊긴 연결을 정책(`ReconnectPolicy`: 최대 5회, 1초부터 지수 증가, 상한 30초)대로 다시 맺음. 모두 실패하면 `FAILED` 로 끝남(무한 반복 안 함) |
| `getStatus()` | `state`, `realHardwareConnected`, 마지막 신호 시각, 오류 수·마지막 오류, 재연결 횟수 |
| `subscribeEvents(handler)` | **정규화된** 표준 이벤트만 받음. 구독자가 던져도 어댑터는 멈추지 않음 |
| `normalizeEvent(raw, receivedAt)` | 장치 원본 → 표준 이벤트. 던지지 않고 `{ok:false, reason}` 으로 돌려줌 |

| 구현 | 설명 |
|---|---|
| `BaseSensorAdapter` | 구독자·정규화·오류 집계·재연결 공통 동작. 하위 클래스는 `openConnection` `closeConnection` `parseRaw` 만 구현 |
| `SimulatorSensorAdapter` | 시뮬레이터용. 출처 `SIMULATED`, **연결돼도 `realHardwareConnected` 는 항상 false**. 연결 전에는 신호를 받지 않음 |
| `HardwareSensorAdapter` (추상) | **실제 하드웨어 확장 지점.** 출처 `REAL`. `CONNECTED` 일 때만 "실제 하드웨어 연결됨"으로 보고 |
| `UnconfiguredHardwareAdapter` | 지금 등록된 자리. 항상 `NOT_CONFIGURED`("연결된 장치 없음"), 연결을 시도하면 "설정되어 있지 않습니다" 오류. 연결된 척하지 않음 |

상태 확인: `GET /api/system/sensor-adapters` (로그인 필요). 실제 하드웨어가 없으면 `hardware: NOT_CONFIGURED, realHardwareConnected: false`.

### 표준 센서 이벤트

```jsonc
{
  "eventId": "evt-20261118-0001",      // 8~64자 영문·숫자·-·_. 같은 ID는 한 번만 처리
  "deviceId": "dev-entrance-01",       // 등록된 센서의 장치 번호(Sensor.deviceId)
  "eventType": "MOTION",               // MOTION(움직임) | STATUS(상태 신호)
  "occurredAt": "2026-11-18T14:03:21Z", // 센서가 신호를 만든 시각. 시계가 없으면 receivedAt 과 같음
  "receivedAt": "2026-11-18T14:03:22Z", // 어댑터가 받은 시각(서버 시계)
  "payload": {}                         // MOTION: 비어 있어야 함(엄격). STATUS: { batteryPercent?: 0~100, firmware?: string }
}
```

- `payload` 는 정해진 항목만 받습니다. 움직임 신호에 "낙상" 같은 값을 끼워 넣어도 거부됩니다(이 서비스는 낙상을 판정하지 않습니다).
- 배터리 정보를 주지 않는 센서는 `batteryPercent` 를 생략하면 됩니다. 서버는 값을 만들어 내지 않고 `UNKNOWN` 으로 표시합니다([SENSOR_HEALTH.md](SENSOR_HEALTH.md)).

### 처리 순서와 오류 처리 (`SensorEventGateway`)

1. **중복 제거(빠른 길)**: 같은 `가구|장치|이벤트ID` 는 기억하는 동안(24시간, 최대 5천 건) 통과시키지 않음 → `DUPLICATE`. 서버를 다시 시작하면 기억은 비워지지만 **DB의 (센서, 이벤트ID) 유일 제약이 최종 보장**합니다(테스트로 확인).
2. **센서 식별**: `(가구, 장치 번호)` 로 등록된 센서를 찾음. 다른 가구가 같은 장치 번호를 써도 섞이지 않음. 없으면 `REJECTED/UNKNOWN_DEVICE` — **모르는 장치의 센서를 자동으로 만들지 않습니다.**
3. **출처 확인**: 어댑터 출처와 센서 출처가 다르면 `ORIGIN_MISMATCH`. 시뮬레이터가 실제 센서의 기록을 만들거나 그 반대가 되지 않습니다.
4. **비활성 센서**: `SENSOR_DISABLED`.
5. **수집 서비스 호출**: 움직임은 `ingestEvents`(너무 오래됨·미래 시각은 `TOO_OLD`·`FUTURE_TIMESTAMP` 로 거부), 상태 신호는 `recordHeartbeat`.
6. **처리 중 오류(DB 접근 실패 등)**: 던지지 않고 `ERROR` 로 알리고 기억에서 지워 **같은 신호를 다시 받을 수 있게** 합니다. 어댑터 구독자의 실패는 집계(`errorCount`)만 하고 어댑터를 멈추지 않습니다.
7. 정규화에 실패한 신호는 구독자에게 가지 않고 어댑터의 오류로 집계됩니다.

## 통신 방식 검토

현재 하드웨어 정보가 없으므로 **선택이 아니라 비교**입니다. 아래는 일반적인 특성이며, 이 프로젝트의 실제 장치로 확인한 값이 아닙니다.

| 방식 | 장점 | 부담·주의 | 이 프로젝트에서의 판단 |
|---|---|---|---|
| **HTTP API** | 가장 단순함. 장치가 서버로 **보내기만** 하면 되어 공유기·방화벽 뒤에서도 동작. 이미 구현됨(장치 토큰, 중복·시간 검사, 요청 제한). 디버깅이 쉬움 | 신호마다 연결을 새로 맺으면 배터리·지연 부담(TLS 포함). 서버가 장치에 먼저 말을 걸 수 없음 | **1순위.** Wi-Fi 센서가 움직임이 있을 때 깨어나 보내는 방식에 잘 맞음 |
| **MQTT** | 가벼운 상시 연결, 재연결·재전송(QoS)·"마지막 유언"(연결 끊김 알림) 지원, 센서가 많아지면 유리, 서버→장치 명령 가능 | **브로커(Mosquitto 등)를 따로 운영**해야 하고 장치별 계정·TLS 관리가 필요. 재전송(QoS 1)은 **중복 전달**이 생길 수 있음(→ 중복 제거가 이미 있음) | **2순위.** 센서가 늘거나 항상 켜진 허브가 생기면 `HardwareSensorAdapter` 를 상속해 구현 |
| **WebSocket** | 양방향 상시 연결, 브라우저·서버 모두 표준 | 장치 쪽 라이브러리·메모리 부담이 MQTT 보다 큼, 연결 상태 관리를 서버가 직접 해야 함, 장치용 표준 규약(QoS·유언)이 없음 | 장치 통신에는 MQTT 가 더 적합. 웹 화면의 실시간은 이미 Socket.IO 를 씀 |
| **BLE** | 저전력, 근거리. 배터리 센서에 흔함 | **BLE 만으로는 인터넷에 닿지 않음** — 휴대폰·허브(게이트웨이)가 필요. 웹 브라우저의 Web Bluetooth 는 지원 범위가 제한적(예: iOS Safari 미지원)이라 앱·허브 없이 웹만으로는 어려움 | **센서가 BLE 라면 허브(예: ESP32·라즈베리파이)가 BLE 를 받아 HTTP/MQTT 로 전달**하는 구성. 서버는 BLE 를 직접 다루지 않음 |
| **Wi-Fi 센서** | 허브 없이 직접 연결, 설치가 쉬움 | Wi-Fi 는 통신 "방식"이 아니라 **전송 수단**(그 위에 HTTP/MQTT 를 씀). 전력 소모가 크고, 공유기 변경·비밀번호 입력(최초 설정) 문제, 공유기 거리·끊김 | 가장 현실적인 형태. 프로토콜은 HTTP(우선) 또는 MQTT |

**제안:** 우선 **HTTP API**(이미 동작)로 시작하고, 센서가 BLE 이거나 많아지면 **허브 + MQTT** 를 `HardwareSensorAdapter` 로 추가합니다. 어느 쪽이든 서버의 규칙·알림 코드는 바뀌지 않습니다.

## 센서 등록

1. 보호자가 **센서 관리 → 센서 등록**에서 이름·구역(침대 주변/이동 경로/현관)·**장치 번호**(위 고유 식별자)를 입력합니다. 같은 가구 안에서 장치 번호는 중복될 수 없습니다.
2. 서버가 **장치 토큰**을 만들어 **한 번만** 보여 줍니다(서버에는 해시만 저장). 분실하면 재발급합니다.
3. 센서에는 아직 신호가 없으므로 상태가 "첫 신호 대기(PENDING)"입니다. **첫 신호를 받은 뒤에만 "연결됨"** 으로 표시됩니다.

## 센서 인증

- 현재(HTTP): `Authorization: Bearer tsn_…` 장치 토큰. 256비트 무작위 값이고 서버에는 해시만 있으며, 센서별 요청 제한과 "사용 안 함" 센서 거부가 적용됩니다.
- 어댑터 방식(MQTT 등)을 추가할 때: **장치별 자격**(토큰 또는 클라이언트 인증서)을 써야 하며, 공용 비밀번호 하나를 모든 센서가 쓰지 않습니다. 브로커는 장치가 **자기 주제(topic)에만** 게시하도록 권한을 제한해야 합니다. 이 부분은 **아직 구현·설계 확정하지 않았습니다.**
- `deviceId` 는 센서를 알아보는 용도일 뿐 **인증이 아닙니다.**

## 실제 센서 연결 절차 (하드웨어가 정해진 뒤)

1. 위 "필요한 하드웨어 정보"를 확보하고, 통신 방식을 고릅니다.
2. HTTP 라면 어댑터 없이 **수집 API 계약**([INGEST_CONTRACT.md](INGEST_CONTRACT.md))에 맞게 펌웨어/허브가 호출합니다. (바로 가능)
3. 다른 방식이면 `HardwareSensorAdapter` 를 상속해 `openConnection`·`closeConnection`·`parseRaw` 를 구현하고, 컨테이너(`container.ts`)의 `SensorAdapterRegistry` 에서 `UnconfiguredHardwareAdapter` 를 교체한 뒤 `SensorEventGateway.attach(adapter, householdId)` 로 가구에 연결합니다.
4. 센서를 등록하고 장치 번호를 맞춥니다.
5. 센서 상세에서 **연결 끊김 기준**(신호 간격에 맞춰)과 배터리 보고 여부를 확인합니다.
6. 실제 신호를 보내 **움직임 기록 → 알림 → 화면**이 시뮬레이션과 같은 결과인지 비교합니다. 이때 **실제 장치로 확인한 항목만** "확인됨"으로 적습니다.
7. 연결 끊김(전원 분리)·배터리·중복 전송·시계 오차를 실기기로 시험합니다.

## 시험 방법

- 자동 시험(이미 있음, 실제 하드웨어 불필요): `apps/server/src/integrations/sensors/sensors.test.ts`
  - 정규화(올바른 신호·시각 생략·형식 오류 11종), 중복 제거(만료·가득 참·재시작 후에도 DB로 방어), 재연결(실패→성공, 횟수 초과, 간격), 구독 해제·구독자 오류, 하드웨어 자리의 "연결된 장치 없음", 시뮬레이터 어댑터, 게이트웨이(HTTP 수집과 **같은 분류·알림**, 모르는 장치, 다른 가구, 출처 불일치, 비활성, 시간 규칙, 상태 신호·배터리, DB 오류 후 재시도), 어댑터 상태 API
- 수동 시험: 시뮬레이터(`/dev/simulator`, `npm run sim`)로 같은 흐름을 재현할 수 있습니다([SIMULATOR.md](SIMULATOR.md)).

## 현재 미구현·미확인

- **실제 하드웨어 어댑터는 하나도 구현하지 않았습니다.** (`UnconfiguredHardwareAdapter` 는 자리일 뿐입니다.) MQTT·WebSocket·BLE 어댑터, 브로커, 장치별 인증서·계정 관리는 설계도 확정하지 않았습니다.
- **시뮬레이터 화면은 아직 어댑터가 아니라 HTTP 수집 API 로 신호를 보냅니다.** `SimulatorSensorAdapter` 는 같은 게이트웨이에 연결되는 어댑터 구현이고 자동 시험으로 확인했지만, 컨테이너가 이를 가구에 자동으로 붙이지는 않습니다(어댑터는 가구 하나에 묶여야 하기 때문).
- 어댑터 상태(`/api/system/sensor-adapters`)는 **설정 → 연동 현황의 "센서 연결 방식"** 카드에 표시합니다(실제 하드웨어가 없으면 "연결된 장치 없음"·"실제 하드웨어와 연결되어 있지 않습니다"). 센서 하나하나의 연결 상태는 이 카드가 아니라 센서별 마지막 신호로 계산한 값(센서 관리)입니다.
- 위 통신 방식 비교는 일반 특성의 정리이며 이 프로젝트의 장치로 확인한 값이 아닙니다.
